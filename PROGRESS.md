## Incident — production 403s against the target's marketing page — 2026-08-01

**What happened:** during the soak, the real target (the site was switched at some point after session 1 from the original dbank login page to the bank's marketing-site login page) started returning `403 bad_status:403` on every pulse check. 83 consecutive fails over ~80 minutes, correctly triggered exactly one DOWN alert (no dupes) and stayed DOWN the whole time — the state machine behaved exactly as designed even under a real, sustained outage-shaped failure.

**Root cause (confirmed by direct testing, not assumed):** it wasn't a real outage or a Cloudflare JS challenge. Plain `httpx` gets TLS/HTTP2-fingerprinted and 403'd by the host's edge WAF (`server: Pantheon`, `x-pantheon-serious-reason: The page could not be loaded properly`) regardless of headers/User-Agent — the block happens at the TLS ClientHello, before headers are even read. Headless Playwright was *never* blocked (real Chromium's TLS stack passes cleanly) — only the `httpx` pulse check was affected. Verified directly: plain `httpx` → 403, `curl_cffi` with `impersonate="chrome"` → 200 with full page + required text, headless Playwright → 200 the whole time.

**Fix:** swapped `monitor/check.py`'s `pulse_check()` from `httpx` to `curl_cffi` (`AsyncSession().get(..., impersonate="chrome")`), preserving the exact same `fail_reason` taxonomy (`timeout`/`dns`/`conn_refused`/`bad_status:<code>`/`nav_error`) by mapping curl_cffi's exception types (`DNSError`, `ConnectTimeout`/`ReadTimeout`, `ConnectionError`, base `RequestException`). `httpx` was unused elsewhere so it was dropped from `requirements.txt` in favor of `curl_cffi` — no dependency net-add, straight swap. Browser check untouched (it was never the problem).

**What was deliberately not done:** a research doc explored heavier options first — residential proxies, browser-as-a-service, monitoring both the marketing page and the separate dbank backend as independent targets, stealth headless drivers (`nodriver`/`patchright`). None of that was needed: a 30-second direct test showed the block was TLS-fingerprint-only on one HTTP client, not a JS challenge or multi-layer WAF. Multi-target monitoring stays out of scope per CLAUDE.md unless explicitly revisited later.

**Verified live:** restarted the running monitor process; it immediately re-checked as UP (200), closed the incident (`duration_s=4827`, `checks_failed=83`), reset state to `UP`/`0`, and fired the real RECOVERY email to the configured recipient.

**Open issue:** if this WAF's fingerprinting rules change again (curl_cffi's Chrome impersonation profile can go stale as WAFs update detection), the same 403 pattern could recur. If it does, re-run the same direct-test approach (plain client vs. `curl_cffi` vs. headless browser against the live URL) before assuming a bigger fix is needed — it was TLS/header, not JS-challenge, both times so far.

## Stage 5 — "It's fast" — 2026-08-04

**Built:**
- `monitor/state.py` — full rework, replacing the old "N consecutive fails" rule with confirmation-burst + confidence-weighted scoring (Rule 2, Stage 5). `MonitorState` gains `burst_started_ts`, `confidence`, `fail_reasons`; drops `consecutive_fails`. New `classify(fail_reason) -> (class, weight)`: hard=2 (`conn_refused`, `dns`, `auth_unavailable`, `bad_status:5xx`, `api_bad_status:5xx`), soft=1 (`timeout`, `element_missing`, `nav_error`, `data_plane_missing`, `api_shape_mismatch`, and any non-5xx `bad_status:`/unrecognized reason — ambiguous evidence defaults cautious rather than hard), config=0 (`auth_rejected`, `bot_challenge`, `mfa_failed`, `rate_limited`). `apply_check()` now takes `layer` and returns `DownEvent`/`RecoveryEvent`/new `ConfigErrorEvent`. Still pure, still no I/O.
- `tests/test_state.py` — rewritten, 20 tests: `classify()` coverage for all three classes plus the unknown-reason fallback; two-hard-fails pages at the second probe (~15s), three-soft-fails pages at the third (~35–40s); a below-threshold single/double fail never alerts; the (F,S,F,F,S) flap sequence never alerts; a stale failure outside `BURST_WINDOW_S` starts a fresh burst instead of compounding a dead one; no duplicate DOWN during a sustained incident; recovery duration math; two restart-from-DB simulations (mid-DOWN, mid-recovery); `CONFIG_ERROR` routing — never scored, never re-alerts, holds through unrelated ordinary failures underneath it, and recovers on the first pass like DOWN does.
- `monitor/check.py` — `CheckResult` gains `layer` (`"pulse"` | `"render"` — the strongest layer a probe actually evaluated). `perform_check()` tags it. New `pulse_only_probe()` / `render_only_probe()` — single-purpose probes for burst re-probing (Stage 5's "vary the probe" rule: pulse and render are independent evidence, unlike two identical retries).
- `monitor/db.py` — `checks` gains `layer`, `burst_id`; `incidents` gains `confidence`, `trigger_layer` (replacing the old `checks_failed`-only shape — `checks_failed` is kept, repurposed as "probe count in the deciding burst/incident"); `state` gains `burst_started_ts`, `confidence`, `fail_reasons` (comma-joined text — no new dependency for JSON). All migrated via `ALTER TABLE` against a pre-existing DB, same pattern as `browser_mode`. Had to split `CREATE INDEX` out of the initial `executescript` and run it *after* migrations — an index on a column that migration hasn't added yet fails on an existing DB (caught by the migration smoke test, see below).
- `monitor/main.py` — burst orchestration runs **inline**, synchronously, inside `run_check_cycle()`: the normal 60s-cadence check is always burst-probe index 0; if it starts a new burst, the remaining `BURST_DELAYS_S` offsets (render, then pulse) run right there with `asyncio.sleep` in between, before the function returns. Deliberately not spawned as a separate task — holding the scheduler's overlap-guard `lock` for the burst's ~40s span means the next 60s tick is correctly skipped/absorbed instead of double-probing mid-burst, with zero new concurrency primitives. Stops early the moment the burst resolves (DOWN fires, or a pass clears it) rather than always running all 3 probes.
- `monitor/channels/email_gmail.py` — `down_message`/`recovery_message` take the event object directly (confidence + fail_reasons + trigger_layer, not a single consecutive-fail count); new `config_message()` for `ConfigErrorEvent`, matching the `[MONITOR-CONFIG]` copy from CLAUDE.md.
- `config.py` / `.env.example` — `FAILS_TO_DOWN` removed; added `BURST_DELAYS_S`, `BURST_JITTER_S`, `BURST_WINDOW_S`, `DOWN_CONFIDENCE`.
- `monitor/web.py` — CSV export includes `layer`/`burst_id` for full audit fidelity; dashboard banner shows the actual status word (`CONFIG_ERROR since ...`) instead of hardcoding "DOWN" for every non-UP state.

**Decisions:**
- Burst probes run inline rather than as a detached `asyncio.create_task` — considered spawning a separate task so the scheduler's 60s loop stays untouched, but that needs a second lock (or careful coordination) to stop the *next* normal tick from racing the in-flight burst against the same DB row. Inline + the existing overlap-guard lock gets the same correctness for free.
- `checks.burst_id` is generated in `main.py` (I/O layer), not `state.py` — a pure function can't emit a random UUID and stay referentially transparent/testable. `state.py` only signals "a new burst started here" via `burst_started_ts == ts`; `main.py` reads that signal to decide whether to mint an ID and keep probing.
- A burst that exhausts all of `BURST_DELAYS_S` without reaching `DOWN_CONFIDENCE` and without a passing probe just... stops, with `state.status` still `UP` and confidence retained. No special "give up" event needed — the next normal-cadence failure either continues accumulating on the same burst (still inside `BURST_WINDOW_S`) or starts fresh (window expired), handled by the same pure rules with no extra state.
- `ConfigErrorEvent` does not open an `incidents` row. An incident is CLAUDE.md's outage record (confidence, trigger_layer, duration); a bad credential or bot challenge isn't an outage, it's a "needs a human" condition, so it only produces the `[MONITOR-CONFIG]` alert.
- Non-5xx `bad_status:` (e.g. a 403 or 404) and any *unrecognized* fail_reason string both default to Soft rather than Hard. CLAUDE.md's confidence table only lists `bad_status:5xx` under Hard — everything else is a judgment call filling a gap in the spec, resolved toward "ambiguous evidence stays cautious" per the project's stated false-positive priority.

**Open issues:**
- Not yet soaked against the real target — `perform_check`/`render_only_probe`/`pulse_only_probe` were exercised via mocks (see acceptance tests below), not a live outage. Worth a short live drill before Stage 6 lands on top of this.
- `BURST_DELAYS_S`'s 60s window and a 60s `CHECK_INTERVAL_S` are close enough that a burst which exhausts its 3 probes without resolving could have its *next* normal-cadence failure land right at the edge of `BURST_WINDOW_S`, going either way (continues vs. fresh burst) depending on exact timing. Inherent to the numbers in the spec, not a bug; flagged here in case it ever needs tightening.

FastAPI's sync dependency-with-yield (`get_conn` in `web.py`) and the route handler it feeds aren't guaranteed to run on the same anyio threadpool worker, so a connection created in one worker occasionally got used from another — intermittent `sqlite3.ProgrammingError` on `/api/status` under real traffic (never surfaced in tests since those don't go through FastAPI's threadpool). Pre-existing since Session 3; only noticed now because this was the first time the dashboard ran live against the Stage-5 code. Fixed by passing `check_same_thread=False` — safe here since each request's connection is only ever used sequentially within that one request, never shared concurrently. ## Structural cleanup tranche B + failure-path hardening ("P0") -- 2026-08-24

**Context.** Human asked whether the codebase is "enterprise-level ready ... refactored so that when it undergoes code reviews, it passes all tests", with a standing instruction to consolidate duplicate/redundant modules and add comments explaining *why* complex methods are written the way they are. That turned into three things in one session: a small consolidation pass, a genuine defect audit (two parallel reviews -- web/DB layer and journey/session layer -- plus direct verification of the most consequential claims), and then the first tranche of fixes. The audit found more than expected, so the honest answer to "is it production ready" was recorded as **no**, with the reasons below rather than a style opinion.

**Consolidation pass (what was and wasn't merged).**
- `config.py`: `validate_core()`, `validate_stage6()` and `scripts/run_signin_drill.py`'s hand-copied field check (whose own docstring admitted it was a copy) now share `_collect_missing()` / `_exit_if_missing()`. Merging them surfaced a latent bug: the drill script's copy omitted `AUTHED_URL`, and a naive merge would have *added* that requirement to a script that never uses it (`run_journey` asserts the authed marker on whatever `LOGIN_URL` redirects to; only `run_authed_check` navigates to `AUTHED_URL`). Resolved with `require_totp` / `require_authed_url` flags so each caller keeps exactly the contract it actually needs.
- `main.py`: the byte-for-byte identical jitter/elapsed/sleep block in `_run_burst_reprobes` and `_run_auth_burst_reprobes` is now one `_sleep_until_offset()` helper, carrying the explanation that was missing entirely -- the sleep is computed as `target_offset - elapsed_since_burst_start`, not a raw `sleep(delay)`, because each iteration already spent real time on DB writes and alert dispatch and a raw sleep would push every later offset further out.
- **Deliberately NOT consolidated,** with reasons recorded so this doesn't get re-litigated: `timeutil.py` stays its own module (imported by both `channels/email_gmail.py` and `web/app.py` -- folding it into either creates a layering violation, duplicating it into both recreates the duplication); `channels/base.py` stays (CONTRIBUTING.md names it the extension seam and lists it under "what NOT to touch"); `web/__init__.py` stays (load-bearing: it is what makes uvicorn's `"monitor.web:app"` string resolve); `session.py` stays (two consumers, distinct security responsibility, and folding it into the already-620-line `journey.py` makes that file worse). `email_gmail._format_duration` stays duplicated from `sms_twilio`'s copy for the same CONTRIBUTING.md reason as before. Agreed criterion going forward: consolidate only when a module has exactly one consumer, no independent tests, and no documented contract role -- file count is not the metric, coupling is.
- Stray on-disk artifacts removed: `data/dev-run.db` (unreferenced manual-drill leftover), all `__pycache__`/`.pytest_cache` trees -- two of which held bytecode for modules that no longer exist (`channels/sms_stub.py`, the pre-package `monitor/web.py`). All gitignored, so none of this was a git-hygiene problem; workspace cleanliness only. The four `__init__.py` files were reviewed: two do real work, and the two empty ones (`monitor/`, `scripts/`) are kept on purpose -- verified empirically that Python 3.3+ namespace packages make them unnecessary for imports and `python -m`, but they keep these as *regular* packages (`__path__` a sealed list rather than a rescanned `_NamespacePath`, so a stray sibling `monitor/` directory can't silently merge in) and setuptools' `find_packages()` only discovers directories that have them.

**Fix 0 -- the documented test command did not work.** `README.md` and `CONTRIBUTING.md` both say to run `pytest`, and that failed at collection on all five test modules with `ModuleNotFoundError: No module named 'monitor'`; only `python -m pytest` worked. Cause: `-m` puts the CWD on `sys.path`, the bare `pytest` executable does not -- under its default prepend import mode it inserts each test file's first non-package parent, so `tests/` (correctly not a package) went on the path and the repo root never did. The suite was green but the command a reviewer or CI would type was broken. Fixed with a fixtureless root `conftest.py`, since pytest always puts the directory holding the topmost conftest on `sys.path`; the reasoning is written into the file so it doesn't read as a mystery empty file.

**Audit findings, and which are fixed.** The two reviews plus direct verification produced one systemic root cause and a set of specific defects, verified live against the running instance where possible.

*The systemic one:* `cycle_scheduler` launches each cycle with `asyncio.create_task` and never awaits it, so **any** unexpected exception in `run_cycle` surfaced only as asyncio's "Task exception was never retrieved" on stderr -- no `checks` row, no `cycles` row, no state advance, no alert. Reproduced with a standalone harness: cycles `[0, 1, 3, 4]` written, minute 2 simply absent. For a monitor this is the worst failure mode, because a quiet dashboard reads as "the bank is fine". This is the amplifier that made every other defect below dangerous rather than merely untidy, and it is what "P0" fixes.

*Fixed in this session (P0):* unbounded credentialed login loop (below); unguarded Playwright calls throughout `journey.py`; strict-mode crashes from ambiguous `.env` locator text; malformed `TOTP_SECRET` raising `binascii.Error` mid-probe; `capture_masked_screenshot` able to destroy the very `CheckResult` describing a failure; `save_session_state` able to turn a successful login into a reported outage; orphaned `checks.cycle_id` rows on a crashed cycle.

*Found and NOT yet fixed -- carried forward as P1/P2/P3:* `/docs`, `/redoc` and `/openapi.json` are served **unauthenticated** (verified live: `200` while `/api/status` correctly `401`), contradicting the docstring's claim that `/healthz` is the only open route, and uvicorn binds `0.0.0.0`; `/api/export?table=all` with empty filters (the default state of the "Download Logs" button) materialises both unbounded tables in RAM inside the monitor's own process -- measured 715-736 MB peak RSS and ~35 s GIL-bound at one year of data, i.e. an OOM kill of the monitor on the planned B2s VM; `journal_mode` is `delete` with no WAL, so a long export read blocks the cycle's write and raises `database is locked` after 5 s (reproduced: 1.42 s block, hard failure at a 7 s read) straight into the silent-task path; `uptime_pct` counts only `verdict='UP'` while a latched auth `CONFIG_ERROR` makes every cycle write `verdict='CONFIG_ERROR'`, so the dashboard reads **0.0% uptime for a bank that is up every minute** (contradicts Rule 13, and the backlog notes a stuck CONFIG_ERROR can only be cleared by a manual DB edit); `/healthz` returns 500 rather than its designed 503 on an uninitialised DB because the web layer never calls `init_db`; empty dashboard credentials authenticate (`compare_digest("","")` is `True`, verified) which is unreachable via `python -m monitor.main` but reachable via `uvicorn monitor.web:app`; date filters compare browser-local time against UTC strings lexicographically; `SESSION_STATE_PATH` defaults inside the OneDrive-synced repo and `os.chmod(0o600)` is a **silent no-op on Windows** despite `session.py`'s docstring asserting it (no session file exists today, so nothing has leaked -- but `run_signin_drill --keep-session` would sync live bank cookies to the org tenant); `MASK_TEXT` is unset and not required by `validate_stage6`, so with `MASKING_ENABLED` defaulting true the mask list is empty and a full-page authed screenshot is captured **unmasked with no warning** (the loud warning only covers the explicit opt-out) -- and because masking uses `get_by_text`, which matches text nodes, it structurally cannot redact an `<input>` value, so the banking login ID appears in plaintext in any post-submit failure screenshot regardless of `MASK_TEXT`. `data/artifacts/` was checked: all ~100 existing PNGs use `check.py`'s public-page `<ts>.png` naming from the 2026-08-06 DNS outage, so none are authed captures.

*The biggest design finding, deferred deliberately because it needs a spec decision, not a patch:* **the authed layer's own definition of DOWN is currently unreachable.** `run_authed_check` has exactly three outcomes, and "page loaded but the authed marker isn't there" -- literally Rule 4's "online banking behind login not rendering", which is v3.8's definition of the platform being down -- is hard-mapped to `session_expired`. Per Rule 17 that leaves state completely untouched, which also means it never sets `burst_started_ts`, so the auth burst never even starts for it. Compounding: `page.goto`'s `Response` is discarded and every authed `CheckResult` passes `http_status=None`, and Playwright does not raise on HTTP error status -- so `bad_status:5xx` is unreachable on this layer too, and a 500 error page behind login produces **zero** DOWN evidence and spends a recovery login instead. Only repeated connection-level `nav_error`s can page the auth track. Stage R acceptance criterion (b) cannot pass as written unless the induced failure is network-level.

**P0 fix 1 -- unbounded credentialed login loop (Rule 11 was bypassable).** `_run_full_login` called `db.append_login_event` only after `run_journey` returned normally. `_login_budget_allows` derives the entire budget -- both `MAX_LOGINS_PER_DAY` and the `LOGIN_INTERVAL_S` gap -- from that table. So any exception in the journey wrote no row, the ledger read as untouched, and because the crash also preceded `save_session_state` the session never became fresh either: the next cycle 60 s later judged the budget clear and logged in again. Unbounded credentialed attempts against a real bank account, invisible in the audit trail, with each cycle vanishing silently via the systemic path above. The ledger is now written in a `try/finally` (with a nested guard so a ledger-write failure can't mask the original exception, and can't replace it on the failure path). Recorded as `reason="internal_error"` when there is no result at all.

**P0 fix 2 -- every Playwright call now maps onto the closed taxonomy.** Only `page.goto` and the username-field wait were guarded, and the only exception type the `classify_*` helpers caught was `AssertionError` from `expect()`. Everything else -- `fill`, `click`, `press`, `is_visible`, the logout click -- could raise `PatchrightError`/`PatchrightTimeoutError` and take the cycle down. New `unexpected_fail_reason()` maps timeouts to `timeout` and everything else to `nav_error`, both deliberately Soft (weight 1): a timeout is genuinely indistinguishable from a hung site, and a strict-mode violation or crashed target is a failed browser *operation* rather than an observation that an element was absent, so `nav_error` is the more honest word than `element_missing`. Outer guards wrap both `run_journey` and `run_authed_check`, placed **outside** the `async with open_journey_browser(...)` so they also catch `new_context()` raising on a truncated/corrupt session file -- which happens before any page exists to screenshot, and which previously killed the auth track on every cycle until a human deleted the file (`is_session_fresh` only stats mtime and never validates the JSON, and `main.py`'s recovery path keys off a result that was never produced). Also: `.first` added to `error_banner` and both `authed_marker` branches (free-text `.env` values with no arity validation were raising strict-mode `Error`, which no handler caught, from four separate call sites); malformed `TOTP_SECRET` now returns `mfa_failed` instead of raising `binascii.Error`; `capture_masked_screenshot` returns `None` instead of raising, mirroring `check.py`'s `_save_screenshot`, because it runs from `_fail()` and the likeliest trigger is precisely the most important failure to report; `save_session_state` is guarded so a caching failure logs a warning (no secret in the message) and leaves the login reported as the success it was.

**P0 fix 3 -- cycle-level self-health net.** `guarded_cycle` now catches everything `run_cycle` can throw, prints the traceback, and writes a `cycles` row with `verdict='DEGRADED'`, `fail_layer='monitor'`, `fail_reason='internal_error'`. **DEGRADED is deliberate:** Rule 13 guarantees it never pages, and a bug in the monitor is not evidence about the bank -- manufacturing a DOWN here would create exactly the false positive this project ranks above every other concern. The row is written **directly, not through `apply_check`**, so it cannot touch either track's state or contribute to any burst's confidence or probe floor; a test asserts the state table is unchanged before and after. The marker write is itself guarded, since the DB may be the thing that broke. `guarded_cycle` also now owns the `cycle_id` and passes it into `run_cycle`, so probe rows already committed before a crash stay reachable from the cycles row instead of being orphaned (a `cycle_id` with no `cycles` row is invisible to `/api/history` and the drill-down, which read `cycles`) -- that also closes part of the reconciliation gap in Stage R acceptance (d).

**Three consequences stated rather than hidden.** (1) `internal_error` and `fail_layer='monitor'` are **new vocabulary** not previously in CLAUDE.md's closed taxonomy; they never reach `classify()`, so they cannot score, but the spec needed amending rather than leaving them undocumented -- see CLAUDE.md v3.9. (2) `uptime_pct` counts only `verdict='UP'`, so DEGRADED minutes now count against uptime. That is arguably correct -- the platform's real state during a blind minute is genuinely unknown, so it is not UP -- but it is the same denominator question as the latched-CONFIG_ERROR defect above and belongs in that fix, not this one. (3) A **residual risk deliberately accepted and documented in `unexpected_fail_reason`'s docstring**: a *persistent* monitor-side bug (a locator that always matches two elements, say) now looks identical to a real soft outage, and four soft probes reach `DOWN_CONFIDENCE`. The 3-probe floor stops a single flake, not a systematic defect. Properly fixing that needs a distinct non-scoring "monitor error" class in the taxonomy, which is a spec decision, so it is flagged rather than silently assumed safe.

### Stage H P1 -- web/DB hardening (same session, 2026-08-24)

Four fixes, all from the audit above, all with permanent tests this time rather than throwaway smoke scripts.

**P1.1 -- the interactive API docs were public.** `FastAPI()` was constructed with default `docs_url`/`redoc_url`/`openapi_url`, so `/docs`, `/redoc`, `/openapi.json` and `/docs/oauth2-redirect` carried **no auth dependency at all** -- verified live against the running instance returning `200` unauthenticated while `/api/status` and `/api/export` correctly returned `401`. That directly contradicted `app.py`'s own docstring ("basic auth on everything but /healthz") and handed anyone who could reach the port the complete route map, including the export and artifact endpoints and their parameter shapes. Since uvicorn binds `0.0.0.0`, on a shared corporate network that is every colleague. Now `FastAPI(docs_url=None, redoc_url=None, openapi_url=None)`. Stage 7 will put this behind Tailscale, but defence in depth belongs in the app, not only in the network topology.

**P1.2 -- unset dashboard credentials admitted everyone instead of denying everyone.** `require_auth` compared against `config.DASHBOARD_USER or ""`, and `secrets.compare_digest("", "")` returns `True`, so with the credentials unset `curl -u ":"` authenticated (verified). `validate_core()` does require both and `main()` calls it, so `python -m monitor.main` was never exposed -- but `uvicorn monitor.web:app` is a perfectly natural thing for an operator to type and never touches `validate_core`, which is exactly how a dashboard ends up accidentally public. Now returns `503 "credentials are not configured"` when either value is falsy, before any comparison. The `or ""` fallbacks are gone but both comparisons still run before the `and`, so there is still no username-vs-password timing oracle.

**P1.3 -- WAL.** `PRAGMA journal_mode` was `delete` (verified) with the default 5s `busy_timeout`. Rollback-journal mode takes a whole-database lock, so a dashboard CSV export's SHARED lock genuinely blocks the cycle loop's `append_check()` from taking its EXCLUSIVE lock at commit -- measured earlier at a 1.42s stall behind a large export and a hard `database is locked` failure once a 7s export outlasted the timeout. That exception fires in `append_check` *before* `apply_check`, so the probe was lost entirely. P0's net now records such a minute as DEGRADED rather than dropping it silently, but recording a self-inflicted blind minute is damage control, not a fix. Now `journal_mode=WAL` + `busy_timeout=15000` on every connection, which suits this app's exact shape (one long-lived writer in the asyncio loop, short-lived per-request readers). Documented in-code: WAL is a persistent property of the *file* so setting it per-connection is idempotent; it adds `-wal`/`-shm` sidecars (confirmed created, and `data/` is already gitignored so no `.gitignore` change was needed); and it does **not** work reliably on network filesystems, so moving `DB_PATH` to an SMB/NFS share would require revisiting this.

**P1.4 -- the "Download Logs" button could OOM-kill the monitor.** `/api/export?table=all` with empty date filters -- the default state of the dashboard page -- called `.fetchall()` on both unbounded tables, turned each into a list of dicts, then `"".join()`ed each entire CSV into one string, all inside the single process that also runs the cycle loop (Rule 8: there is no second process to absorb it). Measured at one year of data: 715MB peak RSS for the fetch, 736MB once the CSV string existed, ~35s GIL-bound. Two operators clicking it during an incident is an OOM kill of the monitoring system, at precisely the moment it matters. Fixed in three parts: new `db.iter_export()` yields row-at-a-time off a live cursor (its `_EXPORT_ORDER` dict doubles as the table allowlist, so a table name still only reaches SQL via a dict key -- a test asserts an injection-shaped name raises `KeyError` rather than building a query); the single-table route now streams from it, with the generator owning and closing the connection in its own `finally` so an abandoned download can't leak it; and the zip -- which genuinely cannot stream, since the format has to seek back and write a central directory -- is written member-by-member via `bundle.open(...,'w')` so the CSV *text* never exists as one string, behind a 200k-row-per-table cap. **The cap 413s with a message naming the row count and pointing at the unlimited streaming path, rather than silently truncating**, because a partial audit export presented as complete would be worse than refusing (Rule 6). `export_cycles`/`export_checks` are deliberately kept for the bounded callers and the tests.

**Also fixed: a shadowing footgun, documented in `monitor/web/__init__.py`.** Its `from monitor.web.app import app` re-export binds `app` in the package namespace to the FastAPI *instance*, which shadows the `monitor.web.app` *submodule* -- so `import monitor.web.app as m; m.SOME_CONSTANT` raises `AttributeError` because `m` is the app object. This cost a real debugging detour: a first pass at verifying the export row cap patched the constant on the FastAPI instance, concluded the cap was broken, and only a direct check showed the cap was fine and the *test* was wrong. The correct handle is `sys.modules["monitor.web.app"]`, which is what `tests/test_web_hardening.py` uses. Left as a documented gotcha rather than renaming the submodule, because `"monitor.web:app"` is what the README and any systemd unit already reference and keeping that stable is worth more.

**Verified.** `pytest` **96/96** (was 80): +16 in the new `tests/test_web_hardening.py`, the first automated coverage the web layer has ever had. Same validation method as P0 -- `git stash`ing the fixes and re-running: **11 of the 16 failed against the pre-P1 tree**, so they are regression tests for real defects (the 5 that passed either way are the companion guards: `/healthz` still open, API still 401/200, zip members still reconciling, date filter still narrowing). starlette's `TestClient` needs `httpx2`, which is not a project dependency and CLAUDE.md requires stop-and-ask before adding one, so the tests drive the ASGI app directly with a small local helper; getting that helper right was itself instructive -- `receive()` must *block* after delivering the body, because returning `http.request` repeatedly busy-loops starlette's disconnect watcher (hang) while returning `http.disconnect` immediately makes it abandon the response body (empty output). The critical assertion is that the streamed export is **byte-identical** to the old materialised path for both tables, and that the zip members are byte-identical to the corresponding single-table exports -- Rule 6's row-for-row faithfulness survives the rewrite. Also ran the patched app for real: WAL sidecars appear next to the DB and a genuine `verdict=UP` cycle row was written.

**One P1-adjacent thing deliberately left alone:** `/healthz` still returns 500 rather than its designed 503 on an uninitialised DB (the web layer never calls `init_db`). It is in P2, not P1, because it only manifests when the web process is pointed at a fresh or wrong `DB_PATH` -- worth noting that the new test suite documents the current behaviour (`status in (200, 503)`, asserted as "not 401") rather than pinning the bug.

### Stage H P2 -- correctness pass, and one regression P0 had introduced (same session, 2026-08-24)

Human asked "is P2 needed, what does it do?" and judged P3 likely unnecessary, with the standing priority being *legible, sensible, optimal code* rather than spec completeness. Answering that question honestly turned up something that changed the ordering.

**The regression P0 introduced, found while answering the question.** Tracing the corrupt-session-file case before recommending anything: `is_session_fresh` only stat'ed mtime, so a truncated or half-written `session_state.json` (process killed mid-write, full disk, reboot during the Node driver's write) counted as fresh. `new_context()` then raises on unparseable `storage_state`, before any page exists. Pre-P0 that killed the auth track silently every cycle until a human deleted the file. **Post-P0 the outer guard dutifully turned it into `nav_error` every cycle instead** -- and traced through `apply_check`, four Soft probes go confidence 1/2/3 then DOWN on the fourth, so a damaged *local* file would have paged a false DOWN carrying Rule 4's authed wording ("online banking behind login not rendering") within about a minute, against a completely healthy bank. `_run_auth_probe` also wouldn't route it to recovery (it keys on `session_expired`, not `nav_error`), so it would never self-heal. That is precisely the false positive CLAUDE.md ranks above every other concern, it was created by P0's own fix, and it was the residual risk P0's `unexpected_fail_reason` docstring described without connecting it to this trigger. Fixed at the source: `is_session_fresh` now also parses the JSON (parse only, deliberately not a schema check -- intactness is the failure mode being guarded, and a structurally-valid-but-wrong session correctly falls through to `session_expired`, which Rule 17 already handles). A damaged file reads as "no session", which routes to the budgeted recovery login, rewrites the file, and **self-heals with no page and no human**. `tests/test_session_freshness.py` pins it, including a test that asserts the four-probe-to-DOWN behaviour so the reason it matters stays visible.

**Uptime denominator.** `uptime_pct` counted only `verdict='UP'` over *every* cycle, so anything not literally UP was downtime. Because the stored verdict is `worst_of(main, auth)`, one stale `LOGIN_PASSWORD` -> `auth_rejected` -> CONFIG_ERROR made every subsequent cycle write `verdict='CONFIG_ERROR'` (main.py holds the track there until a human clears it, and per the backlog the only way to clear it today is a manual DB edit) -- so the dashboard reported **0.0% uptime for 24h/7d/30d while pulse and render passed every single minute**. An audit-grade number describing a total outage that never happened. The denominator now counts only cycles that produced platform evidence, `verdict IN ('UP','DOWN')`; CONFIG_ERROR and DEGRADED are excluded from both sides. Rule 13 already said CONFIG_ERROR isn't an outage; the arithmetic now agrees with the rule. DEGRADED is excluded on the same grounds -- Rule 18's self-health row means "we could not measure", and an unmeasurable minute is not a minute of downtime. Accepted consequence, stated in the docstring: a window containing only excluded verdicts has an empty denominator and reports `None` -> "n/a", not "100%" -- reporting 100% would be the same class of lie in the opposite direction, and the banner is already saying CONFIG_ERROR/DEGRADED next to it to explain why. Also fixed a latent `SUM`-over-zero-rows NULL that would have become a `TypeError`.

**`cycles.authed_ok` conflated "failed" with "never looked".** `_run_auth_probe` returns a synthetic `session_expired` result when there's no usable session and the recovery login was either paused (Rule 16, precursor DOWN) or refused by the budget (Rule 11). `run_cycle` wrote `authed_ok = auth_result.ok` -> `False`, i.e. the dashboard's authed badge went red and the CSV recorded an authed failure when nothing had contacted the platform at all -- directly against Rule 16's own wording that NULL is what means "the track didn't run". `_run_auth_probe` now returns `(result, probed)` and the cycles row writes NULL for `authed_ok`/`authed_latency_ms` when `probed` is False. Chose an explicit flag over sniffing the synthetic result, which would have been fragile. Note a real cheap check that genuinely returns `session_expired` still counts as `probed=True` -- that *is* an observation, just an inert-for-scoring one. The `cycles` schema comment was updated too (audit-grade table; the comment previously enumerated only two NULL cases).

**The authed layer can report an outage again -- the P3 item that was actually a functional bug, so it got fixed rather than deferred.** `run_authed_check` mapped *every* "page loaded but the authed marker is missing" to `session_expired`. Rule 17 makes that completely inert: no score, no probe-floor credit, and critically it never sets `burst_started_ts`, so the auth burst never even started. Net effect: "online banking behind login not rendering" -- Rule 4's exact authed wording and v3.8's literal definition of the platform being DOWN -- **could not be produced by the check whose entire job is to detect it**, and Stage R acceptance (b) could not have passed. Compounding it, `page.goto`'s `Response` was discarded and every authed `CheckResult` passed `http_status=None`; Playwright does *not* raise on an HTTP error status, so a 500 error page behind login classified as `element_missing` -> rewritten to `session_expired` -> weight 0 -> spent a recovery login and produced no evidence whatsoever. Three changes, ~40 lines: the response status is now read and a >=400 authed route reports `bad_status:<code>` (5xx is Hard, weight 2, via the existing `classify`); `_fail` gained an `http_status` parameter so the real status reaches the audit trail; and a missing marker is only called `session_expired` when `bounced_to_login()` confirms the expired-session *signature* -- redirected away from the authed route **and** a login form actually present. Both conditions are required deliberately: a redirect alone isn't enough, since a redirect to a maintenance or error page is platform evidence, not a session problem. Still on the authed route with no marker is now `element_missing` -- Soft, scoring, burst-opening. Route comparison ignores query and fragment and trailing slashes (banking apps append session/nonce params freely, and those don't mean you were redirected).

**Empty `MASK_TEXT` now warns.** `MASK_TEXT` defaults to empty and `validate_stage6()` doesn't require it, so the *default* configuration captured a full-page authenticated screenshot with an empty mask list and no warning at all -- the existing loud warning only ever covered `MASKING_ENABLED=false`, the case someone had deliberately chosen. Now the accidental case warns too, since that's the one that ships by mistake. Deliberately NOT promoted to a `validate_stage6()` requirement (human's call: warning over ceremony). The structural limit is documented in the same comment and stands unfixed: `get_by_text` matches text nodes, so masking can never redact an `<input>` value, and the banking login ID will therefore appear in plaintext in any post-submit failure screenshot regardless of `MASK_TEXT` -- `auth_rejected` being exactly the state a human is asked to go investigate.

**`/healthz` degrades instead of 500ing.** `get_connection` creates the DB file if absent but only `cycle_scheduler` ever calls `init_db`, so a web process pointed at a fresh or wrong `DB_PATH` hit an empty database and every query raised `no such table: checks` -- an unhandled 500 to a systemd or Tailscale-side probe, in exactly the startup window the endpoint's own `503 "no checks recorded yet"` branch was written for. Now catches `sqlite3.Error` and returns `503 {"status":"unhealthy","reason":"database not readable: OperationalError"}` (verified). Deliberately does **not** call `init_db`: the schema owner is the monitor process, and a health probe silently creating tables would hide the very misconfiguration it exists to report.

**Verified.** `pytest` **117/117** (was 96): +7 in `tests/test_session_freshness.py`, +14 in `tests/test_p2_correctness.py`. Same validation method as P0 and P1 -- stashing the fixes and re-running: **12 of the 21 new tests failed against the pre-P2 tree**. `compileall` clean; the patched app ran a real cycle to `verdict=UP`; `/healthz` on a deliberately empty DB confirmed returning 503 rather than 500.

**Explicitly dropped from P3, by decision rather than oversight:** `MASK_TEXT` as a required setting (warning is enough), and a non-scoring monitor-error class in the taxonomy -- validating the session file removed its only known realistic trigger, so Rule 18c's limitation remains true in principle but has no demonstrated path to fire. **Still open and needing a human decision:** `SESSION_STATE_PATH` defaults inside the OneDrive-synced repo tree (latent -- no session file exists today, but `run_signin_drill --keep-session` would sync live bank cookies to the org tenant), and `os.chmod(0o600)` is a silent no-op on Windows despite `session.py`'s docstring asserting it; both need a path choice, not a code change. Everything previously outstanding still is: Stage 6's deferred acceptance drills, the three flagged `classify_*` judgment calls, `TOTP_SECRET` still not captured, the CONFIG_ERROR clear/retry control, the post-Stage-7 `main.py` split and `config.py` Settings conversion, and Stage 7 itself -- which is now unblocked on the P0/P1/P2 grounds that were holding it, pending live verification of all three.
## Stage 6 closeout: MFA locators fixed against real markup, two operator scripts, `.env.example` reorganized -- 2026-08-25

**Trigger:** the auth track sat parked in `CONFIG_ERROR` with `bot_challenge`, on a site that was serving the sign-in flow normally in a visible browser. This is flagged `classify_*` judgment call #1 (see the `journey_unknown_fallback_review` note) **confirmed as a live bug**, not a judgment call: the monitor was reporting a bot challenge where there was none.

**Diagnosis.** `mfa_heading()` matched exactly one string, `"Secure login"`, which is not a heading this flow ever renders. The real step-up flow has **two** screens, each with its own heading: `"Login Security"` (the factor picker -- Text / Call / Authenticator rows) and `"Verify Information"` (the code-entry screen that follows). `mfa_heading()` is what tells `classify_after_submit()` "we reached MFA" and `classify_after_totp()` "we left MFA", so matching neither screen meant the classifier fell through to its `bot_challenge` fallback every time -> Rule 10 -> `CONFIG_ERROR` -> logins halted. The wall it named was real, but it named the wrong wall, which is exactly the failure Rule 4 exists to prevent one layer up.

**Instrument first, fix second (`scripts/dump_dom.py`, new).** The previous locators had been written from screenshots, and screenshots are what produced the wrong strings -- so the first thing built was a way to read the real markup. `dump_dom.py` walks the sign-in flow and writes, per frame, an `elements.txt` (visible interactive elements with inferred ARIA role, approximated accessible name, and a ready-to-paste `get_by_role(...)` line) plus that frame's serialized `page.html`, into `data/dom_dumps/<run ts>/NN_<label>/`.

Two deliberate design choices in it. (1) It **does not use `journey.py`'s MFA locators** -- those were the suspects, and automating past a screen with a locator that may be wrong is how you get zero information. It drives only the three login-form locators known to work (fill credentials, submit), then hands the visible browser to the human: click through the flow yourself, press Enter at each screen to capture it. (2) It **changes nothing** -- imports `monitor/` code for browser setup only, never writes the database, never touches monitor state, never saves a session, never logs out. ## CLAUDE.md v3.9 -- `MAX_LOGINS_PER_DAY` removed; `LOGIN_INTERVAL_S` becomes the single login limit -- 2026-08-26

**Trigger:** a live incident on the dashboard at 15:13-15:17 EDT -- five consecutive cycles of authed `FAIL (session_expired)` on a session that was working perfectly at 15:12 and logged in first-try at 15:18.

**Diagnosis (no code changed during the investigation):**
- The five rows were `latency_ms=0.0` with no screenshot artifact, i.e. `main.py`'s synthetic `_session_expired_result()`, not a real `run_authed_check()` failure. No browser was ever launched. The only route there is `session.is_session_fresh()` returning False.
- Root cause was a **skew between two clocks that were both set to 600s**. `save_session_state()` runs inside `run_journey()`'s stopwatch (before the return), so the session file's mtime is stamped at ~19:02:30 UTC. `db.append_login_event(ts=_now_iso())` runs *after* `run_journey()` returns -- and browser/driver teardown hung for **exactly 300.1s** that cycle -- so the login row was stamped 19:07:30. `SESSION_MAX_AGE_S` counts from the file, `LOGIN_INTERVAL_S` counts from the row. Session went stale at 19:12:30; the budget didn't open until 19:17:30. Five dead minutes.
- Confirmed by SQL across the whole run: normal post-journey overhead is ~0.3-0.5s, and there are **zero** `session_expired` rows anywhere else in a 100-minute stretch. Two outliers found: 300.1s (2026-08-26, this one, on a *successful* login) and 1015.7s (2026-08-25, on a `bot_challenge` failure, so no session was written and no skew resulted).
- Rules held throughout: Rule 17 kept `session_expired` at weight 0, no burst opened, verdict stayed UP, no incident row, no page. The bug was cosmetic-plus-blind-spot, never a false alert.

**Separately diagnosed while in here (2026-08-26 evening, sparse dashboard rows):** the hourly-ish cycle rows from ~16:10 EDT onward are **macOS sleep**, confirmed against `pmset -g log`. **Why removal rather than a bigger cap:** `LOGIN_INTERVAL_S` already bounds the daily total by arithmetic -- at 120s a permanently broken login attempts once every 180s (~20/hour, ~480/day), so any cap above that is decorative and any cap below it only exists to fire. And firing was the bad outcome: the auth track stopped attempting logins until UTC midnight while `session_expired` kept scoring 0, so the platform read UP on zero authed evidence with no alert. The daily cap was the *sole* cause of that silent-blindness mode; removing it deletes the failure mode. Worst case is now "retries every 3 minutes indefinitely," which is honest and self-heals when the site returns. **If a total ceiling is ever wanted back, Rule 11 now requires it raise CONFIG_ERROR on exhaustion.**

**Why 120 specifically:** the dead window opens whenever `LOGIN_INTERVAL_S + skew >= SESSION_MAX_AGE_S`. At 600 it tolerates 0s of skew (the bug). At 300 it tolerates 300s -- exactly the observed skew, i.e. borderline. At 120 it tolerates 480s. 120 also collapses the blind window when the bank invalidates a session mid-life: recovery now happens in the same cycle instead of up to ~7 minutes later. Note the achievable rate is **not** `3600/LOGIN_INTERVAL_S` -- attempts only start on `CHECK_INTERVAL_S` boundaries and the attempt itself burns time before being recorded, so spacing is `ceil((LOGIN_INTERVAL_S + login_duration) / CHECK_INTERVAL_S) * CHECK_INTERVAL_S`. 120 + ~18s rounds up to 180s, stable for login durations from ~2s to ~40s.
